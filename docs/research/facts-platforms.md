# 事實：平台框架

查證過的外部事實，一條一個編號（`P` 加流水號），編號不重用，別處用編號引用。索引在 [brief〈事實索引〉](../design-brief.md)。

## 事實


- **P1** iOS：密碼欄與電話欄由系統強制換回系統鍵盤；App 可用 `shouldAllowExtensionPointIdentifier` 拒絕第三方鍵盤。[Configuring a custom keyboard interface](https://developer.apple.com/documentation/uikit/configuring-a-custom-keyboard-interface)、[App Extension Programming Guide](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/CustomKeyboard.html)。
- **P2** iOS：沒有 Full Access 時無網路、App Group 共享容器唯讀；開了才能網路、寫共享容器、iCloud。[Configuring open access](https://developer.apple.com/documentation/uikit/configuring-open-access-for-a-custom-keyboard)。
- **P3** iOS：鍵盤擴充有記憶體上限，Apple 不公布數字、隨機型而異（社群說法 30–77 MB，`docs/research/platform-frameworks.md` §3.6，未查證）。實測 iPhone 18 Pro Max、iOS 27.2 的上限是 177 MB：連續佔用寫過的記憶體，7 輪終止前的最後一筆 footprint 都在 176.0–176.8 MB；取到 log 的那一輪 kernel 記 `exceeded mem limit: ActiveHard 177 MB (fatal)`、終止原因 `per-process-limit`；先載入核心與資料包再加壓，上限不變。約 142 MB（剩約 35 MB）時收到記憶體警告。被終止時不產生 `JetsamEvent` 報告，證據要從系統 log 取。核心加速成、詞庫、bigram、簡繁、英文、字根提示六份資料包載入後 footprint 79 MB（字根提示 +14.3 MB），是上限的 45%。旗艦機的上限可能比低階機高。[Creating a custom keyboard](https://developer.apple.com/documentation/uikit/creating-a-custom-keyboard)、[Identifying high-memory use with jetsam event reports](https://developer.apple.com/documentation/xcode/identifying-high-memory-use-with-jetsam-event-reports)；`docs/research/ios-feasibility.md`〈記憶體上限〉，2026-11-10。
- **P4** iOS：免費帳號（Xcode 的 Personal Team）描述檔 7 天過期，最多 10 個 App ID（7 天過期）、3 台裝置、每台 3 個 App；App Groups 開放給免費帳號。官方沒寫 app extension 能否用免費佈建；實測能：鍵盤擴充用免費佈建裝上 iPhone 18 Pro Max（iOS 27.2），在備忘錄打字，擴充讀得到主 App 寫進 App Group 的檔、寫入被拒（`EPERM`）。[About your developer account](https://developer.apple.com/help/account/basics/about-your-developer-account)、[Supported capabilities (iOS)](https://developer.apple.com/help/account/reference/supported-capabilities-ios)；`docs/research/ios-feasibility.md`〈免費佈建與 App Group〉，2026-11-10。
- **P5** iOS：`os_proc_available_memory()` 回傳「目前上限減去 footprint」，官方沒說 app extension 能否用；實測鍵盤擴充裡有值，空擴充 `phys_footprint` 約 10 MB（Debug）、footprint 加 available 恆為 177.0 MB（iPhone 18 Pro Max、iOS 27.2；旗艦機，低階機可能更低）。[os_proc_available_memory](https://developer.apple.com/documentation/os/os_proc_available_memory)；`docs/research/ios-feasibility.md`〈免費佈建與 App Group〉，2026-11-10。
- **P6** `phys_footprint` 是 XNU 的 ledger：匿名頁加被壓縮的匿名頁等，公式沒有檔案映射項（推論不含乾淨的檔案映射頁）；`top` 的 MEM 欄、活動監視器、Xcode 記憶體儀表都讀它。Mac18,5（macOS 27.0.1）實測：malloc 釋放的頁留在 footprint、只被之後的配置重用，`malloc_zone_pressure_relief` 也還不回來；M1 里程碑的六份資料包（檔案共 10.3 MB）加 `Engine` 與佈局載入後 footprint 約 96 MB，佈局走 `qim_layout::validate`（含 JSON Schema）讓執行檔多 3.1 MB。[`osfmk/kern/task.c`](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/task.c)、`man footprint`；`docs/research/ios-feasibility.md`〈Mac 上的資料包記憶體〉，2026-11-10。
- **P7** uniffi 0.32.2 的 Swift 綁定（`qim-ffi`）在 Mac 上接得上核心，打 `anr` 上屏「門口」。每鍵延遲（Apple M6、macOS 27.0.1，同一批 123,330 鍵）p95：原生 42 µs、Swift 經綁定 58 µs、WebAssembly 在 Chromium 55 µs；最重的「選開頭一段」那一鍵 p95 0.74 / 0.76 / 0.89 ms，都遠低於 50 ms。uniffi 沒有 `char` 型別。[uniffi 手冊：Built-in types](https://mozilla.github.io/uniffi-rs/latest/types/builtin_types.html)；`docs/research/ios-feasibility.md`〈綁定開銷〉，2026-11-10。
- **P8** iOS：核心經 `qim-ffi` 接進鍵盤擴充，在備忘錄打 `anr` 首選「門口」、空白上屏「門口」。資料包放擴充的 bundle，載入速成、詞庫、bigram、簡繁、英文五份加 `Engine`，footprint 多 51.4 MB（詞庫佔 41.4 MB），載入後共 64.4 MB，是 177 MB 上限的 36%，比 Mac 同組合少約 27 MB（推論 iOS 的 malloc 重用釋放的頁）；載入 120–138 ms。同一批 123,330 鍵每鍵 p50 45 µs、p95 64 µs，選開頭一段 p95 0.79 ms，比 Mac 慢 3.5–10%（iPhone 18 Pro Max、iOS 27.2；旗艦機，低階機可能更慢、上限更低）。`docs/research/ios-feasibility.md`〈鍵盤擴充接上核心〉，2026-11-10。
- **P9** iOS：詞級 trigram 的記憶體（M3 票 11b，同一台 iPhone 18 Pro Max、iOS 27.2，Debug 組態的鍵盤擴充）：核心加速成、詞庫、bigram、簡繁、英文、字根提示六份資料包載入後 79.4 MB，再載入預算版（檔案 4.60 MB）footprint 留下 +5.6 MB、峰值 +20.4 MB；放寬版（13.89 MB）留下 +23.4 MB、峰值 +71.3 MB（到 150.7 MB），那個程序收到兩次記憶體警告（第一次在 141.9 MB）。各在新程序量一次。`docs/research/ios-feasibility.md`〈詞級 trigram 的記憶體〉，2026-11-11。
- **P10** iOS：App Review 4.4.1 要求鍵盤在沒有 Full Access 時仍可用。[App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)。
- **P11** iOS：只能經 `textDocumentProxy` 讀游標前後文，長度上限官方未寫；沒有 marked text。`docs/research/platform-frameworks.md` §3.2。實測長度由宿主決定、大致按句子切、換行不截斷：備忘錄句中給所在句加前一整句、最多 300 字；Safari 的 `<textarea>` 句中只給所在句、句首給前一句、段首從上一句中間切，最多 100 字；每句 50 字的測試文字只讀得到一兩句（推論，真實文字未測；iPhone 18 Pro Max、iOS 27.2）。`docs/research/ios-feasibility.md`〈上下文長度〉，2026-11-10。
- **P12** iOS：Foundation Models 在鍵盤擴充裡能用，沒有完整取用也行（官方沒寫 extension 能不能用，以上是實測）；iOS 27 起 Apple Intelligence 預設開啟、不能關，iPhone 18 Pro 系列跑 AFM Core Advanced（context 8192）。實測照 plan §7.8 的提示，連續請求約 190 ms，停頓後的第一個請求 8 次在 0.29–0.87 s、4 次要 6–15 s，`prewarm()` 擋不住；擴充的 footprint 第一輪多 3.8 MB（含 iphone-use 造成的畫面重建），推論模型不在擴充程序裡跑（iPhone 18 Pro Max、iOS 27.2；其他機型跑 Core 變體，延遲可能不同）。[Detecting available Apple foundation models](https://developer.apple.com/documentation/foundationmodels/detecting-available-apple-foundation-models)；`docs/research/ios-feasibility.md`〈Foundation Models〉，2026-11-10。
- **P13** macOS：Foundation Models 要 Mac 與 Siri 設成相同的語言，否則回 `modelNotReady`（系統設定的 Apple Intelligence 頁有說明）。Apple M6、macOS 27.0.1 跑 AFM 3 Core Advanced（context 8192）：照 plan §7.8 的格式給 9 條整句的提示，連續請求 p50 333 ms、p95 788 ms（機器忙，load average 約 10）；同一個程序停 5–120 秒後的第一個請求 p50 約 1.3 s，48 次裡 7 次超過 2 s、最慢 2.8 s，新程序的第一個請求約 770 ms；1.4% 的提示被安全過濾擋下。[`scripts/experiments/llm-rerank/README.md`](../scripts/experiments/llm-rerank/README.md)，2026-11-11。
- **P14** iOS：candle 0.11.1（CPU、2 條執行緒）不用改就能編到 `aarch64-apple-ios`，在沒有完整取用的鍵盤擴充裡跑。隨機權重的 Gboard 級 1.4M 參數 CIFG-LSTM 重排一次（6 條路徑各 8 字、上下文 200 字）p95 在 9 ms 內（f32 8.2 ms、q8 6.4 ms）、footprint 峰值 +5 MB 內；青簡級 23M 參數字級 decoder 的 q8 是 55 ms、+47 MB，f32 是 78 ms、+95 MB。這些延遲以前綴快取為前提（上下文只算一次、6 條路徑共用）；Mac 上不共用時上下文 50 字慢約 3.4 倍、200 字慢 4–5 倍。candle 在 aarch64 會另存一份重排過的 Q8_0 權重，q8 的常駐約是檔案（23.6 MB）的兩倍。實測 iOS 會還回釋放的大塊配置、macOS 不會，所以以 footprint 峰值（`task_vm_info` 的 `ledger_phys_footprint_peak`，標頭沒有說明，語意由欄位名與實測推定）為準。iPhone 18 Pro Max、iOS 27.2；旗艦機的記憶體上限可能比低階機高。對這台的 177 MB 上限，加上擴充載入核心與六份資料包後的 79 MB（票 09，含字根提示），23M q8 約 126 MB、在記憶體警告線約 142 MB 以下；f32 約 174 MB，離上限只剩約 3 MB，等於放不下（一次樣本）。`docs/research/ios-feasibility.md`〈小型神經模型〉，2026-11-10。M3 票 07 定了重排看 9 條路徑、口語 p95 18 字，照 Mac 上重量的倍數推估 23M q8 上下文 200 字 p95 約 105–110 ms、峰值約 +62 MB（`scripts/experiments/model-ladder/README.md`）；M3 票 09 在同一台 iPhone 實量 9 條 × 18 字：23M q8 上下文 200 字 p95 84 ms、峰值 +74–75 MB（兩個程序），超過 M3 的 60 MB 上限；1.4M q8 p95 11 ms、峰值 +2.0 MB（`docs/research/ios-feasibility.md`〈小型神經模型〉，2026-11-11）。
- **P15** Android：10+ 只有預設 IME 或有焦點的 App 能讀剪貼簿。[Android 10 privacy changes](https://developer.android.com/about/versions/10/privacy/changes)。
- **P16** Android：`getTextBeforeCursor` 是 IPC，可能回 null 或少於要求的字數。[InputConnection](https://developer.android.com/reference/android/view/inputmethod/InputConnection)。
- **P17** Android：密碼欄仍交給當前 IME，IME 須自己不顯示、不儲存。`docs/research/platform-frameworks.md` §4.3。
- **P18** Android：ML Kit GenAI（Gemini Nano）只允許 top foreground app 推論，背景回 `BACKGROUND_USE_BLOCKED`；IME 是否算前景未查證。[ML Kit GenAI](https://developers.google.com/ml-kit/genai)。
- **P19** Android 11+：IME 可顯示 autofill inline 建議，選取前看不到內容。[IME autofill](https://developer.android.com/identity/autofill/ime-autofill)。
- **P20** macOS：IMK 沒有「游標前 N 字」API，`selectedRange` 等可能回 nil 或 `NSNotFound`；沒有 email / URL 欄位提示，密碼欄只能靠 Secure Event Input 判斷。SDK `IMKInputSession.h`；`docs/research/platform-frameworks.md` §5。
- **P21** Windows：TSF DLL 載入每個宿主程序；密碼欄應停用 text services，不靠 `IS_PASSWORD`；app container 內網路不保證。[InputScope](https://learn.microsoft.com/en-us/windows/win32/api/inputscope/ne-inputscope-inputscope)、[IME requirements](https://learn.microsoft.com/en-us/windows/apps/develop/input/input-method-editor-requirements)。
- **P22** Linux：Wayland text-input-v3 的 surrounding text 上限 4000 bytes，`content_hint` 有 `hidden_text`、`sensitive_data`；GNOME 走 text-input-v3 加 IBus，不實作 input-method-v2。[text-input-v3](https://gitlab.freedesktop.org/wayland/wayland-protocols/-/raw/main/unstable/text-input/text-input-unstable-v3.xml)、[mutter](https://gitlab.gnome.org/GNOME/mutter/-/raw/main/src/wayland/meta-wayland-text-input.c)。
- **P23** 共用核心先例：Rime 系列為 C++ 核心；青簡為 Rust 核心加 macOS / Windows / Android 的 Rust 殼，無 iOS。`docs/research/platform-frameworks.md` §1。
