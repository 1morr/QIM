# 新增輸入方案：模型共用，碼表、參數與基準各方案一份

> 草稿（arch-diet 票 02 從 plan〈核心〉〈輸入方案〉搬來），使用者確認後由票 06 編號寫進 `docs/adr/`。目前只有速成一個方案，這裡記的是加第二個方案時照什麼分工；方案檔的欄位在 `crates/qim-core/src/scheme.rs` 與 `data/schemes/quick.toml`，欄位命名參考 Rime `schema.yaml`。

核心只認方案檔與資料包，方案之間怎麼切換由殼負責，每個方案一個 `Engine`。方案檔由 `qim-databuild` 和它的碼表一起編進方案自己的資料包（`<方案 id>.pack`，ADR 0003），`qim-core` 不讀 TOML；可選的資料包由主 App 下載或從檔案匯入，校驗後放進鍵盤讀得到的位置（iOS 是 App Group，沒有完整取用時鍵盤唯讀即可，`docs/research/facts-platforms.md`），擴充不做編譯（Hamster 的分工）。

| 部分 | 處理 |
| --- | --- |
| 語言模型、重排模型、雲端 LLM | 共用，不重訓：它們評的是輸出文字。例外是吃輸入碼的自由生成模型（青簡 P2C），要逐方案訓練 |
| 空間模型、佈局 | 共用：看的是按鍵位置；字根標籤來自方案檔 |
| 碼表 | 每個方案一份（ADR 0003） |
| 詞庫 | 詞與詞頻共用同一來源，每個方案各建一份碼索引 |
| `β`、`γ`、首選字基準 | 每個方案各自調、各有 baseline，品質不能只靠共用模型保證 |
| 學習 | 計數分方案，個人 bigram 共用 |
| 萬用鍵 | 方案檔的 `wildcard` 選一個方案字母以外的鍵（照 fcitx 表格輸入法每個碼表一個 `MatchingKey`，`docs/research/facts-products.md`）；比對規則共用，倉頡等五碼方案進來時再看每段最多 2 個夠不夠 |
| 容錯 | 速成只做觸控鄰鍵讀法，四種修正的容錯不做（量過沒過門檻，brief〈容錯〉、`docs/research/tolerance.md`）。之後的方案要做時：機制共用，修正過的讀法帶懲罰進 lattice，按鍵位置來自按鍵機率；允許哪些修正、懲罰、啟動條件寫在方案檔，各用含打錯碼的基準調。青簡對形碼與雙拼不糾錯 |

依方案類型，工作量不同：

- 形碼（倉頡）：`max_code_length = 5`，碼表來自已在用的 libcangjie。排序和查碼不必改；長碼連打的切分歧義多，開工時定預設連打或逐字。
- 音碼（拼音、粵拼、注音）：多兩件事。一是字與詞的讀音資料，含多音字，來源與授權在開工時查（rime-cantonese 授權鏈未查明，`docs/research/facts-tables.md`）。二是查碼：分隔符、簡拼、懶音不是查一份碼表能做的，要加一種查碼方式。排序和學習不動，所以 lattice 只經一個查碼函式取得候選邊，方案檔再加欄位選查碼方式；現在不先抽象，加第一個音碼方案時才做。

## Consequences

- 手寫純文字方案檔在裝置上匯入要把編譯搬進主 App，等第一個使用者要自訂方案時再做。
