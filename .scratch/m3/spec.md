# M3 智慧候選

由 plan §7.4、§7.8 細化（2026-11-11）。拆票後以票為準；票與本檔衝突時改票或改本檔，並在 progress〈偏差與決定〉記一行。

## 目標

讓候選看得懂上下文、學得到使用者的接續習慣，並量清楚每一層模型值不值得：

1. 上下文：輸入框的前文接進同步層的 n-gram，首選字基準加「有前文」的集合證明它有用。
2. 模型階梯實驗（下面〈模型階梯實驗〉）：同步、停鍵、雲端三層（plan §2.7、ADR 0005）各用什麼模型，依數字決定，不憑印象。
3. 個人模型與輸入增強：個人 bigram、聯想、常用語、自動記住 email 這類字串、emoji 候選、詞庫匯入。
4. 雲端：在階梯結論劃定的範圍內接雲端 LLM，送出前遮蔽、有每日上限、標示來源（brief §8）。票 11 的結論是不做（雲端沒過門檻，票 22 wontfix）。
5. 資料：資料包 manifest 與線上更新、繁體模式的簡體字排序、完整粵語詞庫（授權查清後）。

全部先在網頁做完、Playwright 實打讀回；平台殼在 M6 起一次接上。

## 共同規則

- 沿用 M1、M2 的：依賴用 `cargo add` / `npm install` 取當時 stable，與 plan §1.4 不同時同一 commit 更新該表，版本相關 API 先查 context7 或官方文件；新 crate 或新依賴先改 plan §1.3 與 `xtask` 的 `RULES`；命名照 plan §0 與 `GLOSSARY.md`，新名詞（上下文、常用語、manifest…）在用到的票補進名詞表；建置產物與下載的來源不進 git；新增或改動開發指令的票同輪更新 `docs/development.md`；候選每頁 9 個。
- 改核心、排序或資料包的票，在票的 `## Comments` 附 `cargo xtask bench --check` 的前後對照（各集合、依長度分組、翻盤清單）；動到學習的另附 `--learning`。數字變差要說明原因；`--update-baseline` 同一個 commit 寫理由（plan §5.2）。固定題在案例通過的那張票加入。
- 個人集只報數字與題號，內容不進 repo、commit、票，也不送雲端；雲端實驗要跑個人集，每次先問使用者（plan §5.2）。
- 雲端 API 會花使用者的錢：key 只放本機環境變數（`DEEPSEEK_API_KEY`、`ANTHROPIC_API_KEY`），不進 repo 與瀏覽器儲存空間；缺 key 時跳過雲端部分並註明；每張票第一次真的呼叫付費 API 前，把估計的請求數與費用告訴使用者、等同意。自動化測試一律攔截請求（Playwright 的 route），不打真的 API。
- 動到網頁的票，除了 Playwright 腳本，再實際操作網頁亂按一輪（組字中夾雜各種鍵、快速連按、切換模式與新開關）；找到的問題先寫成會紅的 Playwright 測試再修。截圖存 `.scratch/m3/evidence/`。
- 會改寫打出的字或改變候選位置的新行為都有開關，預設值照 brief §7；新開關進 `Options`，網頁設定頁照現有選單的樣子加。
- 新資料來源釘進 `data/sources.toml`（版本、sha256、授權、取用的檔案），每個資料包的 `LICENSE`、`NOTICE` 只寫它用到的來源（plan §4）；新資料包加進 `cargo xtask data --verify` 的決定性檢查。
- 實驗放 `scripts/experiments/<名>/`，各有 README（日期、機器與系統、版本、commit、量法、結果表），實驗的 crate 不進 workspace；結論先寫 `docs/research/`，再摘進 brief〈查證過的事實〉並連結。
- 對外格式：學習資料匯出 v2 在 M3 收尾前還沒發佈，M3 的票可以往 v2 加列的種類，收尾票定稿並寫進 plan §2.4；v1 的匯入一直要收。資料包 manifest 也是對外格式，設計時先看成熟產品（例如 Rime 的 `rime-install` 與 plum、Gboard 的語言包），採用誰的慣例寫在票裡。
- 要使用者決定或動手的事（階梯的採用門檻、付費 API、建 GitHub release、口語語料來源），到了就在該票停下問，不阻塞其他票。推到遠端與在 GitHub 上建任何東西前先問。

## 模型階梯實驗

由 plan §7.8 搬來（2026-11-11）。要回答：同步層、停鍵層、雲端層（plan §2.7）各用哪個模型，修正次數和首選正確率能改善多少，延遲、大小與費用是否可接受。現在的路線從字級 bigram 直接跳到 LLM，中間的選項都要量過。

- 前置：M1 的 `rerank_request` / `apply_rerank` 介面與首選字基準；M2 量完的記憶體上限、Foundation Models、上下文長度與小型神經模型開銷（`docs/research/ios-feasibility.md`、brief §12.3）；M3 的 `set_context` 與「有前文」集合。
- 模型大小上限（M2 票 09）：iOS 鍵盤擴充裡，模型的 footprint 峰值增量 ≤ 60 MB，讓核心加資料包（79 MB）加模型留在記憶體警告線（約 142 MB）以下；23M 級只能用 q8（+47 MB）。數字來自 iPhone 18 Pro Max，只限 iOS 鍵盤擴充。
- 測試集：維基、口語、個人三個集合，加「有前文」的集合。結論以口語為主；個人集原本也是，票 25 起只報不擋（〈採用門檻〉）；維基集只防退步。
- 受測模型：

| 層 | 模型 | 備註 |
| --- | --- | --- |
| 同步 | 字級 bigram（基線）、字級 trigram、詞級 n-gram | 同一份預算（≤ 8 MB）比較，再看放寬到 M2 上限時的增益；另量一份不設預算、可選下載的詞級 trigram（CyIME 是 105–203 MB，`docs/research/cyime.md` §3） |
| 停鍵 | 小型神經模型：Gboard 級（約 1.4M 參數）、青簡級（約 23M 參數） | 自己用 plan §4.3 的語料訓練，重排前 N 條路徑（N 與路徑長度由基線票定，M2 票 11 用的 6 條、8 字是近似）；放不進上限就只量桌面；實作做前綴快取（上下文只算一次，路徑共用），不共用時慢 3–5 倍（brief §12.3） |
| 停鍵 | Apple Foundation Models | 這台 Mac 上用 Swift 命令列跑；另量停頓後第一個請求的延遲尾巴（M2 在 iPhone 上 12 次裡 4 次 6–15 s） |
| 雲端 | DeepSeek `deepseek-flash`（關閉思考模式），`deepseek-v4-pro` 當對照 | 經 OpenAI 相容介面（brief §12.4）；開工時重查模型清單與價格 |

- 提示（LLM）：上下文 + 輸入碼 + 前 10 個候選，要求模型只回序號（afm-ime 做法，`docs/research/open-source-imes.md` §5）；實驗可試幾種寫法，採用的那種由雲端重排票照搬。
- 指標：修正次數、首選正確率、「最高到第 2 位」規則下的前 2 名命中率，各和基線比；資料包或模型大小、常駐記憶體、載入時間；每次請求或推論的延遲 p50 / p95；雲端每千次請求費用；上下文長度 0、50、200 字各量一次（iOS 實際多半只有數十字、最多 100–300 字）。
- 採用門檻：基線票量完基線後提出，使用者確認後寫進下面〈採用門檻〉，之後的實驗票不改它，避免看到結果才定標準。
- 基線票（票 07）定的，之後各票照用（細節與數字在 `scripts/experiments/model-ladder/README.md`）：
  - 調參與報數分開：各票調參數（λ、權重、提示寫法、N）只看 dev 切分（`build/corpus/<名>/dev.tsv` 與 dev 的長前文題）；test 與個人集只在設定定案後跑一次報數，採用門檻也只看那一次。個人集不切：它是使用者自己的詞，切一半調參就是對著答案調，也只剩一半題數；所以個人集不參與調參。
  - 指標：首選正確率與修正次數照首選字基準；「最高到第 2 位」的前 2 名命中率是首選加上模型排的第一個不是首選的文字。重排只動第 2 位起，而模擬選第一頁任何一個都算一次修正，所以停鍵層與雲端層改變不了首選與修正次數，只看前 2 名命中率；首選與修正次數是同步層的指標。
  - N = 9 條 lattice 路徑（`Session::paths`），路徑長度 p50 7 字、p95 18 字（口語 dev）；重排模型看候選列第一頁加這 9 條。候選列只放 3 條多段路徑，答案在候選列的比例（口語 dev 57%）比在前 9 條路徑（68%）低。
- 訓練出來的模型受語料授權影響，與 bigram 同列 brief §11。
- 產出：`scripts/experiments/model-ladder/` 的腳本與 README（日期、模型版本、結果表）。結論票把各層的採用與不採用理由寫回 brief §12、§1.5、§11，必要時改 brief §8 的 200 字上限；採用小型神經模型時改 plan §1.3、§1.4 並另建 crate（plan §2.7）。採用的項目各補一張實作票進〈票序〉、擋收尾票；雲端的範圍（只重排、加雲端聯想與補全，或不做）也在結論票定，並改寫雲端各票。

### 採用門檻

票 07 提出，使用者 2026-11-11 確認（四項都照提案），之後的實驗票不改；唯一的例外是使用者在票 25 把個人集那條改成只報不擋（下面〈共同規則〉）。基線與量法：`scripts/experiments/model-ladder/README.md`。

基線（test 切分，字級 bigram 加 `set_context`；2026-11-11 合併 main 到 `02217b1` 後重量，票 16、18 等改了資料包）：口語首選 36.3%、前 2 名 49.1%、修正 2.421 次/句、前 9 條路徑有答案 68.0%；個人首選 76.0%、前 2 名 85.5%、修正 0.325 次/句；維基首選 43.8%、前 2 名 55.1%。之後主分支再改資料包或核心時，各實驗票在開工的 commit 重量基線再比，門檻（增量）不變。

共同規則：
- 設定在 dev 切分定案後，test 切分與個人集各跑一次，只看那一次。
- 改善看 test 的口語組（2,638 題）；改善的翻好／翻壞要過 McNemar 精確檢定（雙尾）p < 0.05（`model-ladder compare`）。
- 不退步：維基的首選、前 2 名不低於基線 1.0 點。個人集的首選、前 2 名、修正次數只報、不擋（使用者 2026-11-11 改，票 25；原本是首選、前 2 名各不低於基線 0.5 點、修正次數不多於基線 2%）：個人集取自 Rime 的學習資料，Rime 不看上下文，使用者在 Rime 多半只打短詞；QIM 要能一下打長句、用上下文，不該被這個習慣卡住。只改模型階梯的門檻：`cargo xtask bench --check` 的個人集 baseline 照舊守核心不退步，換模型的票照舊更新並列翻盤。
- 同一層裡較貴的一級要比已採用的較便宜那級再過門檻，只比基線好不算。
- 正確率過了、成本超標的不採用；成本達標、正確率沒過的也不採用。

同步層（字級 trigram、詞級 n-gram；看首選與修正次數）：
- 口語首選 +2.0 點以上（現在的基線下 ≥ 38.3%），且口語修正次數少 3% 以上（≤ 2.348 次/句）。
- 預算版：語言模型資料包 ≤ 8 MB；每鍵延遲原生 p95 ≤ 1 ms、選開頭一段 p95 ≤ 5 ms（這台 Mac，`cargo xtask bench`）；載入 ≤ 300 ms。
- 放寬到 M2 上限的版本（模型峰值增量 ≤ 60 MB）：要比預算版首選再多 2.0 點。
- 不設預算、可選下載的詞級 trigram：口語首選比基線多 4.0 點以上才做；只做桌面與可選下載，不進 iOS 預設。

停鍵層（小型神經模型、Foundation Models；重排改變不了首選與修正次數，只看前 2 名命中率）：
- 口語前 2 名 +4.0 點以上（現在的基線下 ≥ 53.1%）。
