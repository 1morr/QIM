## 怎麼重跑

```sh
cargo xtask data                                    # repo 根目錄；要有長前文題（build/corpus/<名>/*-context-long.tsv）
ln -s <主 checkout>/bench/personal bench/personal   # worktree 裡要個人集時（docs/development.md〈個人集〉）
cd scripts/experiments/model-ladder
cargo run --release -- eval                         # dev 切分的基線，約 50 秒
cargo run --release -- eval --split test            # test 切分加個人集：只在設定定案後跑一次
cargo run --release -- export [--split test] [--n 9] [--include-personal]
cargo run --release -- eval --orders <結果.jsonl> --name <模型名>
cargo run --release -- compare ../../../build/model-ladder/dev/baseline ../../../build/model-ladder/dev/<模型名>
```

- `eval` 印 Markdown 表，逐題結果寫到 `build/model-ladder/<切分>/<模型名>/<集合>.tsv`（只有行號與數字，個人集也一樣）。
- `export` 把每題的重排要求寫成 `build/model-ladder/<切分>/requests/<集合>.jsonl`（下面〈給實驗票〉），不含答案。個人集要加 `--include-personal` 才匯出；它的內容只在本機、不送雲端，雲端實驗要跑個人集每次先問使用者（plan §5.2）。
- `compare` 比兩個逐題結果目錄裡同名的集合：首選、前 2 名、可動首選各報翻好／翻壞與 McNemar 精確檢定（雙尾）的 p 值。

## 量法

### 集合

| 組 | 集合 | dev 切分 | test 切分 |
| --- | --- | --- | --- |
| 維基 | yue-wiki、zh-wiki | `build/corpus/<名>/dev.tsv`（各 2,000 句） | `bench/corpus/<名>.tsv` |
| 口語 | common-voice-yue、hkcancor | `build/corpus/<名>/dev.tsv` | `bench/colloquial/<名>.tsv` |
| 有前文 | 四個語料各 `·前文0`、`·前文50`、`·前文200` | `dev-context-long.tsv` | `test-context-long.tsv` |
| 個人 | personal | 不切（下面〈調參與報數〉） | `bench/personal/rime-userdb.tsv` |

- 有前文：和基準的「有前文」集合同一批題，前文改用同一段裡前面最多 200 字（`cargo xtask data` 寫的長前文題，plan §5.2）。`·前文0` 不給前文（同基準的 `·前文·不給`），`·前文50`、`·前文200` 給最後 50、200 字。核心只看前文的最後一字（plan §2.3），所以基線的 50 與 200 一樣；給重排模型的前文才有差別。長前文有多長：維基段落常超過 50 字，口語多半只有一兩句（test 的長前文 p50 是 8–79 字，見下面〈限制〉）。
- 每題用新的 `Session` 與空白的 `UserModel`，同首選字基準。

### 指標

- 首選正確率、修正次數：照首選字基準算（`qim_bench::score_set`，和 `cargo xtask bench` 同一份程式），定義見 `docs/development.md`〈首選字基準〉。
- 前 2 名命中率（「最高到第 2 位」規則，ADR 0005）：打完整串輸入碼、不選字，重排模型回它排的文字；顯示的第 1 名是核心的首選（不動），第 2 名是模型排的第一個不是首選的文字（模型沒排就照核心的第 2 個）。答案在這兩個裡就算命中。
- 可動首選時：模型自己排的第一名是答案的比例。ADR 0005 不讓重排動首選，這欄只當參考（`docs/research/neural-rerank.md` §5 建議兩種接法都量）。
- **重排改變不了首選與修正次數**：首選不動；修正次數的模擬選第一頁任何一個都算一次，第一頁內怎麼排都一樣。所以停鍵層與雲端層只看前 2 名命中率，首選與修正次數是同步層（票 08）的指標。
- 召回：答案在候選列的前 k 個、在 lattice 的前 k 條路徑的比例。後者是重排模型看 k 條路徑時前 2 名命中率的上限。
- 依組合計：每組的集合加起來；「有前文」依語料（維基、口語）與前文長度各一列，另有兩者合計的一列：口語的長前文很短，合在一起時前文長度的差別幾乎都來自維基。結論以口語與個人為主，維基只防退步（spec）。

### 重排模型看什麼

`Reranker::rerank(&Query) -> Vec<String>`。`Query` 有集合名、行號、前文、輸入碼、候選列第一頁（最多 9 個，依核心的順序）與 lattice 的前 N 條路徑及路徑分（`qim_core::Session::paths`）。模型可以挑候選列裡沒有、路徑裡有的文字：候選列只放方案的 3 條多段路徑（`ranking.sentences`），口語 dev 上答案有 56.3% 在候選列，在前 9 條路徑卻有 67.2%。要在產品裡放進候選列，`apply_rerank` 得能插入不在候選列的路徑，這由階梯結論票（票 11）定。

### 調參與報數

- 各票調參（神經分的權重 λ、插值權重、提示寫法、N）只看 dev 切分：維基與口語的 `dev.tsv` 和 dev 的長前文題。四個語料都有 dev 切分（plan §4.3 的 90／5／5，依句子雜湊切，dev 的句子不在 train，也不在 test）。
- test 切分與個人集只在設定定案後跑一次報數，採用門檻（spec〈採用門檻〉）也只看那一次。`--split test` 會印提醒；每次真的跑 test 都記在該票的 Comments。
- 個人集不切：它是使用者自己打過的詞（Rime 的學習資料），切一半拿來調參就是對著使用者的答案調；題數也會少一半。所以個人集完全不參與調參，只在定案後報數。
- 訓練神經模型的語料同樣只用 train 切分，並照 `docs/research/neural-rerank.md` §5 剔除所有評估句（票 09）。

### 讀法

- 重排的上限：口語 test 的前 2 名命中率 49.1%，前 9 條路徑裡有答案的是 68.0%，重排模型最多補 19 點；候選列第一頁裡有答案的只有 55.3%，只在候選列裡挑最多補 6.2 點。
- 個人集的詞短（p50 2 字），基線已經 76.0% 首選、前 9 條路徑 97.0%，重排能補的不多，主要看它不退步。前 2 名比答案在前 2 條路徑（86.6%）低 1 點，合併前只差 0.1 點：候選列的第 2 位有時不是第 2 條路徑，推測是合併進來的 emoji 候選這類由排位規則放進的項目，沒有逐題查。
- 前文：核心只看最後一字，50 與 200 字對基線一樣（表上合成一列）。給前文比不給：口語多 1.5 點首選、1.3 點前 2 名；維基首選少 0.1 點、前 2 名多 0.5 點（同票 04 的結論：合計較好，zh-wiki 持平）。
- 成本（同步層，`eval` 最後一行與 `cargo xtask bench`）：
  - 字級 bigram 資料包 3,018,934 位元組（2.9 MB），解開 2.7 ms（5 次中位數，2.4–2.9）。
  - 常駐記憶體：Mac 上載入後 footprint +12.3 MB、heap 7.5 MB（M2 票 04，`docs/research/ios-feasibility.md`〈Mac 上的資料包記憶體〉）。
  - 每鍵延遲（原生 release，`cargo xtask bench` 的計時）：合併前三次（機器忙、load average 13–18）p50 34.7–36.3 µs、p95 57.0–60.6 µs，選開頭一段 p50 259–273 µs、p95 912–931 µs；合併後一次 p50 32.2、p95 44.1 µs，選開頭一段 229、754 µs。WebAssembly（Node）合併前 p95 69.7–73.6 µs、選開頭一段 1.06–1.13 ms；合併後 53.3 µs、0.89 ms。
  - 沒有費用。

## 給實驗票

- 同步層（票 08）：換掉語言模型資料包或核心的打分，`eval` 照跑；看首選、修正次數與前 2 名，和基線 `compare`。
- 停鍵層的神經模型（票 09）：`src/neural.rs` 的 `Neural`（candle，照 `../neural-cost/`），訓練與結果在 `../neural-rerank/`。
- Foundation Models、DeepSeek（票 10）：`export` 匯出 `Query`，外部程式（Swift 命令列、HTTP）一題回一行 `{"split": 切分, "set": 集合名, "line": 行號, "ranked": [文字…]}`，再 `eval [--split …] --orders <檔> --name <名>`。切分不符就報錯（dev 與 test 的集合名相同）；沒回的題照原順序、報告最後印題數。延遲請在外部程式量，框架內的計時只算 `rerank` 呼叫本身。
- 模型回的文字不在這題的候選與路徑裡就不算（框架丟掉、報告印個數），LLM 憑空寫出答案不會灌高命中率。spec 的提示寫「前 10 個候選、只回序號」：`Query.candidates` 是第一頁 9 個（`RERANK_LIMIT`），序號換回文字由外部程式負責。

## 限制

- 只在打完整串輸入碼時重排一次；實際上使用者可能在停鍵層回來前就按空白，青簡記下過這種競態（`docs/research/neural-rerank.md` §1.7）。
- 前 2 名命中率假設使用者等到結果才看候選列。
- 有前文的題都是整句，前文以標點結尾，核心接句首（plan §2.3）；長前文只多給重排模型看。
- 長前文多長取決於語料：test 的長前文 p50 是 common-voice-yue 8 字、hkcancor 16 字、yue-wiki 54 字、zh-wiki 79 字；到 50 字的比例 0%、17%、54%、66%，到 200 字的 0%、1%、6%、16%（dev 相近）。所以前文 200 字那檔實際上只在維基量得到，口語的 50 與 200 幾乎相同。HKCanCor 每句話是一行，要量口語的長前文得把同一段對話接起來（票 09、10 決定要不要）。
