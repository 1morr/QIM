# neighbor-readings：Gboard 式的觸控鄰鍵讀法值不值得做（M4 票 09b）

- 日期：2026-11-14；機器：Apple M6（Mac18,5，32 GB）、macOS 27.0.1；rustc 1.99.1。
- commit：M4 票 09b 的分支（開工 `75671c4`）。機制在 `330f4b4` 進核心、`a73d849` 刪掉；`012b199` 同時有機制與這個 crate 的第一版，重跑要在它上面（見〈怎麼重跑〉）。dev、test 與第一次的延遲量的時候，同一份機制在另兩個 commit 上，那兩個 commit 的樹被 pre-commit hook 的測試寫壞（`a8cd2cc` 修了測試）、已從分支拿掉；程式從 git 物件找回成 `330f4b4`，在它上面重跑 dev 的 `combo` 和原本逐字相同。
- 問題：票 09 量的容錯（四種修正進整句路徑、單字不修、靠懲罰排名）沒過〈容錯採用門檻〉。Gboard 速成的做法不同（`docs/research/blackbox-baseline.md` T2a）：只靠點擊位置，原樣讀法優先，點在錯鍵中心時想打的詞留在候選列中段，點在交界才當首選；單碼也列鄰鍵的字；漏碼、對調不救。這裡量這種做法：打錯的題能不能在第一頁找回想打的字詞、修正次數少多少、會不會擠到沒打錯的題，每鍵延遲多少。門檻在 `.scratch/m4/spec.md`〈容錯採用門檻〉〈每鍵延遲上限〉，結論在 `docs/research/tolerance.md`〈Gboard 式的鄰鍵讀法〉。

## 機制（`330f4b4` 進核心、預設關，`a73d849` 刪掉）

`qim_core::Engine::with_neighbor_readings(NeighborReadings)`（`crates/qim-core/src/neighbor.rs`）：

- 只收觸控的按鍵機率（`accepts`）。核心分不出觸控與實體鍵盤，實驗把「不是某個字母的實體鍵機率（`qim_bench::physical_key`）」當觸控；實體鍵盤照舊只取機率最高的字母（票面）。
- 原樣的 lattice 不動，另推進一個「鄰鍵讀法的 lattice」：同一串輸入碼，邊另含一段碼裡換一碼成鄰鍵字母才查得到的字詞（單字也換）。鄰鍵字母是這一下的按鍵機率裡、機率至少是打出的字母 `floor` 倍的，最多 `letters` 個；換一碼扣 `weight × ln(打出的 ÷ 換成的)`。一條路徑可以有幾段各換一碼。有分隔記號或萬用鍵的段不換。
- 候選列：鄰鍵讀法的 lattice 蓋滿整串、換過碼的路徑，依分數取最多 `limit` 個，從第 `slot` 格起依序插進原樣的候選列；文字已在它前面的不插，在後面的移上來。原樣的首選照舊在第 1 格。
- 模稜兩可（`ambiguous`）：最好的鄰鍵讀法換的碼的機率比（換成的 ÷ 打出的）乘起來 ≥ 門檻、分數又高過原樣的首選路徑時，它當首選。
- 選了鄰鍵讀法：照換過的碼上屏與學習（基準不學）。選開頭一段、改選某一段後，剩下的輸入碼保留按鍵機率；放回選定的分段的沒有。
- 沒做：debug 面板的標記、停鍵重排、簡體模式的轉換後去重以外的處理；只插蓋滿整串的讀法，不插只蓋住開頭一段的。

Gboard 的放法由 T2a 推（沒補黑箱）：模擬器上的 Gboard 是共用的裝置，補黑箱要改它的語言設定；T2a 的截圖（`.scratch/m1/evidence/09-android-t2a.png`）已看得出放法：

- 單碼 `a` → 日、曰（原樣）、手、田、尸（q、w、s 鍵的字）：單碼的鄰鍵字排在原樣候選之後，一次列三個鄰鍵。
- `am` → 星、旦、**門**、暨…（第 3 格）；`snr` → 刷口、**門口**（第 2 格）、刷、尸、屍、**日**（s→a 的單字，第 6 格）；`amr`、`ane` → 門口在第 5 格；`sn`、`ab` 前 6 格沒有門。看起來是照分數穿插在原樣候選裡，落在第 2–5 格，一頁裡有一到三個鄰鍵讀法。
- 所以這裡掃「從第 2、3、5 格起、最多 1–4 個」，在 dev 比修正次數再定。

## 量法

獨立的 crate（`Cargo.toml` 有空的 `[workspace]`），不在 repo 的 workspace 裡，`cargo xtask check` 不編它；它用路徑依賴 `qim-core`、`qim-bench`、`qim-databuild`、`qim-layout`。改程式後自己跑 `cargo clippy --release --all-targets -- -D warnings`、`cargo fmt --check`、`cargo test --release`。

### 題目與按鍵（看結果前定，協調者 2026-11-13 要求）

- **觸控模擬**（判斷用的集合）：口語兩個語料的觸控題（dev：`build/corpus/<名>/dev-touch.tsv`；test：`bench/colloquial/touch/`），兩個語料合計。點擊照集合的座標經 `SpatialModel` 轉成按鍵機率（同基準）。集合裡本來就有沒打錯的題（test 824 題），沒打錯會不會被拖累、改錯，先看它們。
- **重打也點觸控**：基準的修正次數模擬（`qim_bench` 的 `simulate`）發現打錯後照碼重打時一律送實體鍵，觸控的使用者重打也是點觸控，所以會低估鄰鍵讀法的代價（重打的字照樣冒出鄰鍵讀法擠位置）。這裡把那段模擬複製到實驗裡（`src/main.rs` 的 `simulate`），只把重打的鍵換成「觸控點對鍵」的點擊（下一條），其餘規則照抄。鄰鍵讀法關的時候按鍵只取最高的字母，點對鍵的點擊和實體鍵打出一樣的碼，所以「關」的數字等於基準的觸控基線（test 打錯的題首選 0／1,814、修正 9,892 次，test 的輸出核對得到）。
- **觸控點對鍵**：沿用票 08 的觸控錯誤模型（`qim_databuild::typo::TouchNoise` 的預設值：σx 1.8 mm、σy 1.5 mm、往下 0.6 mm、往中心拉 0.3σx、旋轉 15°，`docs/research/typo-bench-models.md`；同一個佈局與畫布尺寸），抽法同 `qim_databuild::typo::touch_items`，只是點到別的鍵就重抽（原本只在點到字母鍵以外才重抽）。不另發明參數。種子是集合名與行號的 SHA-256，每次一樣。
- **沒打錯的集合改成觸控點對鍵送**：維基、口語、有前文（給與不給前文）各集合，第一次與重打都送觸控點對鍵的點擊，量答錯數、修正次數與被擠的比例，對照〈容錯採用門檻〉沒打錯不退步那條（答錯增加 ≤ 0.5%、修正次數增加 ≤ 1%）。
- **照實體鍵送的集合**（含打錯碼、原本的沒打錯集合、固定題）：機制只對觸控，**設計上不適用**；test 只核對開關前後逐題相同（首選、修正次數、候選列），證明觸控的判斷沒有漏到實體鍵，不寫成過或沒過。
- 個人集：這個工作區沒有，沒跑。

### 指標

- 票 09 的：打錯的題首選、修正次數（整個集合）、「原樣正確卻被改錯」（票 08 的量法：沒打錯、關的時候首選正確的題裡，開的時候首選不正確的比例）、翻好／翻壞（McNemar 精確檢定，雙尾）。
- **想打的整句在第一頁**：打錯的題按完第一次的鍵、不選字，期望的整句在候選列第幾名（最多翻 5 頁、每頁 9 個）；報第一頁的比例、前 5 頁的比例、找得到的平均名次，和關的時候並列，並依期望的字數分組（1 字、2 字、3–4 字、5 字以上）。
- **被擠**：沒打錯的題按完鍵、不選字時，關的時候第一步要選的候選（首選接得上就是首選，否則第一頁接得上的最長候選，同修正次數的模擬），開了之後名次往後的比例、被擠出第一頁的比例；第一頁沒有接得上的題不算。
- 每鍵延遲：基準的每鍵延遲那批輸入（固定題與四個語料的 test 題）與首碼換成 `z` 的那批，每個輸入照觸控點對鍵送；關與開逐題交替，空白與學過（學完各語料與有前文的題的 `UserModel`）各一次，對照〈每鍵延遲上限〉；超過時負載低時單獨重跑一次。

### dev 怎麼挑（看結果前定）

dev 觸控題的按鍵機率（`weights`，只看機率、不看結果）：每一下第二高 ÷ 最高 p10 0.099、p50 0.235、p90 0.447（空間模型保證點中的鍵最高，比值不到 0.5）；點錯的 3,815 下，想打的字母 97% 是第二高（3,702 下），它 ÷ 最高 p10 0.275、p50 0.435。所以 `floor` 掃到 0.3、模稜兩可的門檻掃 0.25–0.45，`letters` 固定 2、`weight` 固定 1（照機率本身）。

1. 放法：`floor` 0.05、不搶首選，從第 2、3、5 格起、最多 1、2、3、4 個，共 12 種。
2. `floor`：照第一步挑到的放法，掃 0.02、0.05、0.1、0.2、0.3。
3. 模稜兩可時搶首選的門檻：照第二步的設定，掃關、0.45、0.4、0.35、0.3、0.25；改錯要 ≤ 1.0%。

每一步挑觸控模擬（兩個語料合計）修正次數最少的；一樣多取打錯的題整句在第一頁較多的，再一樣取先列的（第 2 格先於第 3 格、少的先於多的、門檻關先於開）。沒打錯的集合改成觸控送的那幾批只在挑完後用 `combo` 報（test 才判）。

### test 怎麼判（設定定案後只跑一次）

- 觸控模擬（兩個語料合計）對照〈容錯採用門檻〉的觸控那幾條：打錯的題首選 ≥ 6%、修正次數比關少 10% 以上、翻好／翻壞 p < 0.05、改錯 ≤ 1.0%。
- 沒打錯的集合改成觸控送：各集合答錯增加 ≤ 題數的 0.5%、修正次數增加 ≤ 1%；固定題（觸控送）全過。
- 含打錯碼那幾條與照實體鍵送的集合：設計上不適用，只核對相同。
- 第一頁的比例與平均名次、被擠的比例另報；〈容錯採用門檻〉是為票 09 那種會搶首選的容錯訂的，採不採用由使用者看數字決定。

## 怎麼重跑

核心的機制在 `a73d849` 刪掉，這個 crate 只在留有機制的 commit 上編得過；最新版的 crate（含 code-review 後補的 `single` 與 `--taps`）在分支的最後，取過來放在 `012b199` 上跑：

```sh
git worktree add ../qim-neighbor 012b199   # repo 根目錄；另開一個 checkout，不動目前的工作區
cd ../qim-neighbor
git checkout 1morr/t09b -- scripts/experiments/neighbor-readings   # 合併後換成主分支
cargo xtask data                           # 格式 v8 的資料包與 dev、test 題（或 `--root` 指回已建好資料的 checkout）
cd scripts/experiments/neighbor-readings
cargo run --release -- weights             # dev 觸控題的按鍵機率分布
cargo run --release -- dev                 # 三步挑設定，最後一行印出 test 的參數
cargo run --release -- combo <設定>        # dev 打一種設定，含沒打錯的集合
cargo run --release -- test <設定>         # 只跑一次（code-review 後照同一組設定補跑過一次，見〈結果〉）
cargo run --release -- latency <設定> [--taps noisy]   # 負載低時跑
cargo run --release -- single <設定> [--split test]    # 單字集合
```
